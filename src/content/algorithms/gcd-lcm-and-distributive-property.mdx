## Why It Surfaces

This is a recognition problem. The straightforward route builds two lcms and then takes their gcd, but the intended shortcut is the identity `gcd(lcm(x, y), lcm(x, z)) = lcm(x, gcd(y, z))`.

## Worked Example

- For `x = 3`, `y = 4`, and `z = 10`, compute `gcd(4, 10) = 2`, then `lcm(3, 2) = 6`.
- For `x = 30`, `y = 40`, and `z = 400`, compute `gcd(40, 400) = 40`, then `lcm(30, 40) = 120`.

## Reference Implementations

<ExamplePair>

```js
function gcd(left, right) {
  let a = Math.abs(left);
  let b = Math.abs(right);

  while (b !== 0) {
    [a, b] = [b, a % b];
  }

  return a;
}

function lcm(left, right) {
  return (left / gcd(left, right)) * right;
}

function gcdLcmAndDistributiveProperty(x, y, z) {
  if (![x, y, z].every((value) => Number.isInteger(value) && value > 0)) {
    throw new RangeError("Expected positive integers for x, y, and z");
  }

  return lcm(x, gcd(y, z));
}
```

## Follow-up Questions

- Can you derive the companion identity `gcd(x, lcm(y, z)) = lcm(gcd(x, y), gcd(x, z))`?
- Why is the simplified route preferable even when the direct computation also fits in integer bounds?
- How would you test this identity across many random triples?

## Common Pitfalls

- Computing both lcms first and missing the intended simplification.
- Using the identity without validating the positive-integer assumptions of the standard prompt.
- Multiplying before dividing inside the lcm helper and creating larger intermediate values than necessary.
