## Why It Surfaces

This problem looks like subset sum, but the candidate numbers are implicit: `1^n, 2^n, 3^n, ...`. The interview value comes from seeing that once you process the bases in increasing order, uniqueness falls out naturally from the recursion because you never revisit a smaller base.

## Worked Example

For `x = 10` and `n = 2`, the only valid representation is `1^2 + 3^2 = 10`, so the answer is `1`. For `x = 100` and `n = 2`, there are `3` representations: `10^2`, `6^2 + 8^2`, and `1^2 + 3^2 + 4^2 + 5^2 + 7^2`.

function integerPower(base, exponent, limit = Number.MAX_SAFE_INTEGER) {
  let result = 1;

  for (let count = 0; count < exponent; count += 1) {
    result *= base;

    if (result > limit) {
      return limit + 1;
    }
  }

  return result;
}

function countPowerSumWays(target, power) {
  if (!Number.isInteger(target) || !Number.isInteger(power) || target < 0 || power <= 0) {
    throw new RangeError('target must be a non-negative integer and power must be a positive integer');
  }

  function search(remaining, nextBase) {
    const nextValue = integerPower(nextBase, power, remaining);

    if (nextValue === remaining) {
      return 1;
    }

    if (nextValue > remaining) {
      return 0;
    }

    return search(remaining - nextValue, nextBase + 1) + search(remaining, nextBase + 1);
  }

  return search(target, 1);
}

## Follow-up Questions

- Add memoization keyed by `(remaining, nextBase)` to avoid recomputing overlapping subproblems.
- Return the actual decompositions instead of only the count.
- Compare this search tree with subset sum and explain why candidate reuse is forbidden here.

## Common Pitfalls

- Reusing the same base more than once and accidentally counting non-unique decompositions.
- Calling `Math.pow` repeatedly without an upper bound check and doing extra work after the target has already been exceeded.
- Confusing the count of valid representations with the number of terms in one representation.
